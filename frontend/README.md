# Research Bridge — React frontend

A React + Vite implementation based on the supplied Research Bridge presentation interface and conversation. Keeps the original green/white design, pale green status cards, gold warnings, header/sidebar layout, and responsive reviewer evidence workspace.

## Start locally

Use Node.js 20.19+ or Node.js 22.12+ with npm. Extract this project into your empty `frontend` folder (package.json should be directly inside frontend).

```sh
npm install
npm run dev
```

Open the local address printed in the terminal (normally http://localhost:5173).

```sh
npm test
npm run build
npm run preview
```

Dependencies must be installed on your computer. node_modules and a lockfile are not included; commit the package-lock.json generated by npm install for repeatable installs. This project uses React 18 and Vite 6 with JSX and plain CSS, no Tailwind installation required.

## The changed workflow — no staging

Upload → immediate simulated processing → student edits/checks metadata → explicit confirmation → reviewer assessment → corrections if needed → new document version → processing and confirmation again → reviewer approval → repository publication → Submitted only on publication success.

There is NO staged status, holding period, 24-hour timer, six-hour replacement period or advance-clock control. The short processing animation represents simulated work, not a holding window.

## Important scope boundaries

This is a working local frontend, NOT a connected production submission system. No database, OCR, AI extraction, real student accounts, email delivery, DSpace deposit, repository deletion or server audit protection is implemented by this frontend.

Use fictional documents only in demo mode. Metadata is in localStorage and files in IndexedDB, without encryption. Browser storage is not secure document storage. Local file preview is real; extraction and repository hand-off are simulated.

DOCX files can be retained/downloaded but are not rendered in-browser. PDFs use the browser's built-in renderer; fragment-based page/zoom navigation depends on browser support. Real source highlighting needs page/coordinate evidence from the processing API and a dedicated PDF renderer. The sample's evidence is illustrative and is NEVER represented as actual evidence from your uploaded file. Academic options are fixtures, not an authoritative ABU department directory.

Demo role switching is not access control. IDs/names are fictional; the demo intentionally shares one student's record with the reviewer. Same-origin tabs update through browser storage, but this is not reliable concurrent multi-user synchronization. Simultaneous writers can conflict; a real API must enforce permissions, version checks, idempotency and workflow rules.

Reset removes local metadata/notifications; stored file blobs remain until this site's browser storage is cleared. Keep sensitive files out of the demo. No cross-device persistence is supplied. The same application must be served from the same origin/port for tab synchronization.

## API authentication checkpoint — compatible with the supplied conversation

The supplied latest backend code defines these routes:

- POST /api/v1/auth/login with JSON registration_number and password.
- GET /api/v1/auth/me using the bearer token.
- POST /api/v1/auth/logout returning 204.

Copy `.env.example` to `.env` if you need a different API base URL. Restart Vite after changing it.

On the sign-in screen choose **Test existing API authentication**. The client submits credentials, stores the returned token in memory (not localStorage), calls /auth/me, verifies user identity consistency, and exposes logout. Reloading clears the in-memory session.

Your backend must allow the exact frontend origin through CORS. For localhost development, add CORSMiddleware to the FastAPI application with allow_origins=["http://localhost:5173"], allow_methods=["GET", "POST", "OPTIONS"], and allow_headers=["Authorization", "Content-Type"]. Preserve existing middleware and adjust the origin if needed. Do not expose the development authentication provider in production.

The supplied development account is DEMO/PG/001 with password ResearchBridgeDemo, ONLY if you implemented and enabled the supplied development provider. That provider currently exposes only a student account. Demo role switching is therefore unavailable in API mode.

Successful API login opens an authentication checkpoint rather than pretending that local demo submissions belong to a real authenticated API session. Document endpoints in the conversation were not supplied as verified implementations. No upload requests are sent to assumed endpoints and no failed API call silently falls back to demo authentication.

## Connecting the remaining API later

Keep components and styles. Replace local record operations in App.jsx with real query/mutation operations and server-returned records. Finalize exact paths and payloads against FastAPI's OpenAPI contract, not guessed routes. You will need:

1. Academic option lists and authenticated account profile.
2. Multipart upload and server-side validation, checksums and private object storage.
3. Submission list/details, current file and extraction job status.
4. Versioned editable metadata, student confirmation and evidence locations.
5. Reviewer decisions pinned to file/metadata versions.
6. Structured correction requests, response and corrected uploads.
7. Publication status, attempts, retry investigation and repository history.
8. Notification delivery/read state and protected server audit history.
9. Authorized signed document URLs, secure session lifecycle, polling/events, optimistic concurrency and idempotency.

Authoritative workflow changes must be verified server-side. Never accept a frontend status variable as proof of approval. Remove the simulated processing/publishing effect when connecting workers. Do not add staging timers back.
